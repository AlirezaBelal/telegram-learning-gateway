01 / Purpose

One entrance. Several learning destinations.

A learner should not need to know every course bot before choosing a path. The gateway provides a consistent Persian entrance, then hands the journey to independent course and support destinations.

PHP handles the boundary. It authenticates webhook requests, validates the update, resolves an explicit command and loads the corresponding response module. Deep-link parameters take a learner directly to a known menu.

MySQL holds limited state. Chat identifiers, route state, timestamps and update receipts support continuity and replay handling. The gateway routes learners; it does not deliver a full curriculum or generate AI answers.

02 / System architecture

Authenticate. Route. Commit with care.

This is the intended production architecture documented by the source. It does not represent a running service.

The important transaction boundary

Receipt and learner writes remain uncommitted during the reply attempt. A failed delivery rolls them back and returns 503 so Telegram can retry. A committed receipt suppresses a replay. A lost acknowledgement or failed commit can still repeat a reply: this is not exactly-once messaging.

04 / Engineering decisions

Small modules. Explicit failure boundaries.

Authenticate before persistence
Production is the default. A missing secret fails closed; the supplied header is checked with hash_equals. Non-POST, unauthenticated, oversized and malformed requests are rejected before a database connection.
Bound the request envelope
Input is capped at 1 MiB; JSON decoding uses depth 32. Text and chat identifiers are validated. Known non-private chats and commands addressed to other bots are ignored. Missing chat type remains accepted for legacy compatibility.
Keep routing inspectable
A fixed command map selects five response modules. Unknown text receives a Persian help hint and preserves an existing route. User text is never interpolated into static Markdown replies.
Make delivery failure visible
Parameterized SQL and InnoDB transactions tie state to unique update receipts. The existing cURL client has 5-second connect and 15-second total timeouts and closes its handle. Transport, HTTP and API failures do not report success; no local retry loop is added.
Inspect the acknowledgement boundary

Excerpt from src/processor.php, after receipt and learner writes:

if ($deliver($message['chat_id'], $reply) !== true) {
    throw new RuntimeException('Telegram delivery was not acknowledged.');
}
$pdo->commit();

The surrounding exception path rolls back an active transaction. This protects local consistency; it cannot undo an already received external reply.

05 / Data lifecycle

Store less. Maintain the lifecycle.

Data minimization is an engineering choice, not anonymity or a privacy certification. Chat IDs, state and metadata may still be sensitive.

Stored by the application

  • Chat identifiers and route state.
  • Creation, update and processing timestamps.
  • Message metadata and unique update receipts.
  • Redacted byte-length text by default: [redacted:bytes=N].

Requires operator maintenance

  • STORE_RAW_MESSAGES=false is the default; new updates do not copy profile names or usernames.
  • MESSAGE_RETENTION_DAYS=30 does not delete anything by itself. Schedule the purge command and monitor its exit status.
  • Chat/state rows and historical profile or raw-message data need separate erasure decisions.
  • Once a receipt expires, replay deduplication no longer covers that update.

The website has no learner records, database connection, cookies, analytics, scripts or Telegram API calls. Its Persian examples come from public source code.

06 / Installation reference

Prepare the source in your own environment.

For future developers choosing to install independently. These instructions do not deploy a service or register a webhook. This mission activates no bot.

Requirements: PHP 8.0–8.4 (64-bit), Composer, Git, cURL, PDO MySQL and an InnoDB MySQL database. A live deployment additionally needs operator-controlled PHP hosting, HTTPS and privately configured Telegram credentials.

git clone https://github.com/AlirezaBelal/telegram-learning-gateway.git
cd telegram-learning-gateway
composer validate --no-check-publish
composer install --no-interaction

Database initialization & existing-installation migration

For an independently planned fresh installation, bot_database.sql creates aculearn_bot_database and InnoDB tables. Use a separate schema account; never run this as an unreviewed operation against existing data.

# POSIX shell; schema-admin is your separate installation account
mysql -u schema-admin -p < bot_database.sql

# Windows PowerShell equivalent
Get-Content -Raw bot_database.sql | mysql -u schema-admin -p

For an existing installation, back up first and apply migrations/001_update_receipts.sql to the intended database before deploying. Verify users, user_states and messages use InnoDB; plan legacy engine conversions separately. Check existing message indexes before adding the optional retention index. The bootstrap script already includes update receipts.

Secure deployment & retention reference

GitHub Pages serves static files and cannot execute this PHP/MySQL application. Independent operation needs a separate PHP host. Expose only public/, keep config/.env, SQL, scripts, dependencies and logs outside the document root, and disable directory listing and PHP error display.

Privately configure database credentials, TELEGRAM_BOT_TOKEN, a random TELEGRAM_WEBHOOK_SECRET and the actual TELEGRAM_BOT_USERNAME. Runtime SQL privileges are SELECT/INSERT/UPDATE/DELETE; use a different account for schema changes. Keep tested backups and review migrations before release.

Any future webhook registration is a separate operator action over HTTPS using Telegram’s secret_token option. The app checks X-Telegram-Bot-Api-Secret-Token; never put secrets in URLs. No registration command or active endpoint is provided here.

# Inside an independently configured HTTPS Nginx server
root /srv/learning-gateway/public;
client_max_body_size 1m;
location = /index.php {
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME $document_root/index.php;
    fastcgi_pass unix:/run/php/php8.3-fpm.sock;
}
location / { return 404; }

Adjust the FPM socket and TLS configuration to the actual host. Do not expose parent directories through aliases. Schedule php scripts/purge_messages.php at least daily in that independently operated environment, protect backups, and monitor failures. No maintenance schedule is activated by this website.

08 / Scope

A gateway source project, with clear limits.

This is a static product presentation and technical case study. No live Telegram bot, webhook, PHP service or database is activated here. No learner data or source credentials are provided. External bots have their own availability and responsibilities. This repository is not an LMS, Telegram client or AI tutor; running it requires independent configuration and deployment.

Authentication and transaction boundaries reduce risk. They do not certify security, erase historical data automatically or guarantee exactly-once delivery.
